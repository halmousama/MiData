# i18n — catalogues, keys, coverage

> **Status:** implemented in P0-2 (`midata-i18n`) — catalogues born, lookup live, gate enforcing.
> **Source:** `REBUILD_PLAN.md` §7.4 (i18n), D3 (EN+FR only), D24 (the `midata-i18n` crate),
> AGENTS.md rule 12, owner policy (no Arabic/RTL in v1).
> **API contract:** `crates/midata-i18n/README.md`. This file is the authoring contract.

## 1. One crate, two catalogues

- The catalogues live in **`crates/midata-i18n/catalogues/`**: `en.tsv` is the **source**, `fr.tsv` is
  first-class, not an afterthought.
- `midata-i18n` is L0 and pure: it is shared by the desktop app **and** the CLI, so `CommandError`
  messages, command titles and CLI help are translated by the same lookup as screen labels.
- **Location (settled):** `REBUILD_PLAN.md` §7.4 places the TSV files under
  `crates/midata-i18n/catalogues/`, embedded at build — aligned to D24 in P0-12 (M1). D24 is
  authoritative: the crate is L0 and shared by app and CLI, and this file is its operational form.
  Do not maintain two copies and do not create a second catalogue under `midata-app/`.
- **Lookup is `t!(translator, "key")`, and the translator is an argument.** Architecture §9 forbids
  process globals, so the language is not a `static` and there is no ambient "current language": the
  composition root parses `Catalogue::embedded()` once, builds a `Translator`, and passes it down.
  Params go through `tf!(translator, "key", "min" => "1")`. (This is a deliberate, documented
  refinement of the older `t!("key")` wording: a process-wide language would break the no-globals
  rule and make a two-language snapshot render impossible.)
- Lookup resolves against the compiled catalogue; **no file I/O at runtime**. A missing key returns
  the key itself and is reported by the coverage gate — **never a panic and never an empty string**.
- Language lives in settings (`en` | `fr`, the persisted `Language::code()`), switchable live;
  switching re-renders without a restart.

## 2. TSV format

```tsv
key<TAB>text
screen.dashboard.title<TAB>Dashboard
cmd.animal.create.title<TAB>Create animal
err.animal.duplicate_custom_id<TAB>Tag “{custom_id}” is already used by another animal.
```

- Two columns, tab-separated, UTF-8, no header row, no quoting.
- `{placeholder}` markers are substituted at call sites (params are always passed, never concatenated).
- One row per key in `en.tsv`; `fr.tsv` carries the same keys. A key present only in `en.tsv` is an
  untranslated string and appears in the coverage report.
- Interpolation keeps word order flexible: whole sentences are keys, never sentence fragments glued
  together, because FR word order differs.

## 3. Key naming

| Prefix | Used for | Example |
|---|---|---|
| `screen.<screen>.<part>` | screen chrome, labels, empty states | `screen.animal_list.empty.title` |
| `cmd.<area>.<action>.title` | command titles shown in menus/CLI | `cmd.observation.record.title` |
| `cmd.<area>.<action>.help` | `params_doc` prose (long form) | `cmd.animal.create.help` |
| `err.<area>.<condition>` | `CommandError` messages | `err.animal.sire_not_male` |
| `field.<key>.label` | seeded field labels (data-defined, translated) | `field.milk_yield.label` |
| `insight.<study>.<shape>` | deterministic analytics insights | `insight.trend.rising` |
| `species.<key>.label` | preset species labels (user species carry their own text) | `species.cow.label` |
| `nav.<item>` | navigation entries | `nav.analytics` |

Rules: lowercase, dot-separated, stable like command ids (renaming a key is a code change with a
translation migration, not a cosmetic edit). `title_key` in a command spec is always
`cmd.<area>.<action>.title`.

## 4. What must be translated

Everything a user or an agent can read: UI labels, navigation, empty/loading/error states, command
titles and help, `CommandError` messages, validation-rule messages, insight templates, seed-pack
labels, PDF/export headers, and CLI help. **No exceptions for "internal" messages**: engine-side error
text is a user-facing string by definition (that was a documented weakness of the reference project and
is explicitly not reproduced).

Not translated: machine identifiers (command ids, field keys, species keys, storage keys), log lines
(developer-facing, English), and the AI system instructions (English by decision D10 — the *response*
mirrors the user's language instead; one stabilizing prompt line is allowed).

## 5. Coverage rule

- `cargo xtask i18n-coverage` prints one measurement line — EN total, FR translated/total and
  percentage, FR rows, missing FR, orphan FR, unused EN, and the baseline — then either the four rules
  or the OK line. It fails the build on any of them.
- **Coverage is a ratchet:** it never decreases. EN is 100% by construction (it is the source); FR
  reaches **100% — including engine-side messages — by the end of Phase 6** (a Phase-6 exit gate).
  Two numbers are enforced against `docs/i18n-coverage.baseline`: absolute missing FR keys may not
  increase, and the **EN total may not decrease** — deleting source keys shrinks the denominator and
  would let coverage rise without a string being translated. A genuinely dead key is deleted together
  with its FR row **and** a regenerated baseline in the same change.
- **An orphan FR key is fatal** (P0-2): a row present in `fr.tsv` but absent from `en.tsv` fails the
  gate. It was a printed report line before the catalogues existed; from P0-2 on it is a build break.
  Orphan keys are deleted, not parked: dead keys are dead code.
- **An unused EN key is fatal** (P0-2): a source string that no `crates/` or `apps/` source references
  is a speculative key, and a speculative key is a dead key. "Seed a string when a screen, command or
  error needs it", never before. A key counts as referenced only as a **plain quoted literal** at its
  call site — building keys with `format!` is unsupported by design, because it blinds both the gate
  and an agent's grep.
- **An EN-only string fails the build, now.** The baseline records `fr_missing: 0`, and the ratchet
  is "missing FR keys may not grow", so adding an `en.tsv` row without its `fr.tsv` row is a gate
  failure (`FR coverage regressed: 1 missing key(s), baseline allows 0`) — proven on the merged tree
  in P0-2's first negative proof. Add both rows in the same commit; the "allowed mid-phase" concession
  ended the day the catalogues appeared. No literal user-facing strings in code, ever — a screen or
  command that hard-codes English fails review.

## 6. Adding a string (checklist)

1. Choose the key by the table in §3 — do not invent a new prefix without adding it here.
2. Add the `en.tsv` row and the `fr.tsv` row in the **same commit** (a lone EN row is a coverage
   regression waiting to happen).
3. Use `t!(translator, "…")` at the call site, and pass params through `tf!` — never build sentences
   by concatenation. Reference the key as a plain literal; a key assembled with `format!` fails the
   unused-key rule.
4. For a `CommandError`, return the key + params from the domain error type — the UI/CLI renders it.
   Commands carry the **machine** value in and the user message is translated at the surface, so the
   engine never needs to know the UI language.
5. Run `cargo xtask i18n-coverage`, confirm no drop, and check the FR render on screen (snapshot spot
   check when the change is visible).
